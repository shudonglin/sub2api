Will you hit the 100K ops limit?

Key insight from Prisma FAQ: Array transactions (e.g. prisma.$transaction([query1, query2])) count as 1 operation, not 2. So batching writes is free. Interactive transactions count each query separately.

So which one?

A

Supabase — Share your existing DB

Best if: You want zero cost, zero setup, and your sub2api is already there.

  • No ops limit — never worry about hitting a cap
  • Already set up and running
  • ⚠️ Risk: shared 500MB with sub2api, and your free project limit is used up
  • ⚠️ Risk: pauses after 1 week idle (unlikely for payment system)
B

Prisma Postgres — Separate free DB

Best if: You want payment data isolated and don't want to share storage quota.

  • Separate 500MB just for payments — doesn't eat into sub2api's storage
  • No idle pause — always on
  • Built-in Cloudflare edge caching for reads
  • sub2apipay already uses Prisma ORM — native fit
  • ⚠️ 100K ops limit — fine for <10K orders/month
  • ⚠️ Only 10 pooled connections on free tier
C

Start with Prisma, fallback to Supabase

Best if: You want isolation now but have a safety net.

  • Use Prisma Postgres free tier for payments (isolated, always-on)
  • If you outgrow 100K ops, switch DATABASE_URL to Supabase — Prisma ORM works with both
  • One env var change, zero code changes
